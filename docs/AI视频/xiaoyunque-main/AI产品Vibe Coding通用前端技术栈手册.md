# AI Agent 产品 Vibe Coding 通用前端技术栈手册

> 文档版本：V4.1（MVP 自动视觉上线改造版）  
> 适用范围：Web 端 AI Agent 产品的新建、MVP 开发、已有 MVP 的上线级视觉改造和持续迭代  
> 使用方式：产品经理将本手册与产品需求、PRD、已有 MVP 或当前开发任务一起交给代码型 AI，AI 直接完成技术选型、视觉选型、设计规范匹配、前端改造、分阶段开发和质量检查  
> 主要读者：代码型 AI；产品经理不需要学习或决定本文中的技术内容

---

## 0. 给 AI 的最高优先级执行指令

你是本项目的前端技术负责人和执行者。

收到本手册后，你必须自己完成以下工作：

1. 阅读产品需求、PRD、设计资料、后端接口和已有代码；已有 MVP 时必须先运行并检查真实页面；
2. 根据本手册自动完成前端技术选型，不把技术选择题交给产品经理；
3. 根据产品用户、业务领域、场景和最终产物，从第 14 节自动选择一个主方案包；
4. 没有正式品牌设计时，按第 13 节自动从 Refero Styles 匹配一套具体设计规范，提取可用的 `DESIGN.md`、Tailwind、CSS Variables 和 Design Tokens，不把审美选择题交给产品经理；
5. 核验方案包中的模板、组件、动效和外部资产，优先合法复用，并生成项目专属 `DESIGN.md`；
6. 自动形成页面、组件、状态、接口和测试方案；
7. 按可运行的业务闭环分阶段编码；
8. 将选定设计规范真实写入代码，而不是只输出建议或设计文档；
9. 启动真实项目，在浏览器中检查页面和交互；
10. 执行类型、Lint、测试和生产构建检查；
11. 用普通产品语言汇报结果、未完成项和真实风险。

除非用户明确要求“只做分析或规划”，否则不要只输出建议、技术方案或待办清单。完成必要分析后，应直接进入实现。

你不得要求不懂开发的产品经理选择以下内容：

- React 还是 Vue；
- CSR、SSR 还是 Server Component；
- Zustand、Redux 还是 Context；
- SSE、WebSocket 还是轮询；
- 目录结构、组件拆分和接口封装；
- 测试框架、代码检查和构建工具；
- 是否需要加载态、错误态、断线恢复和移动端适配；
- 应该使用哪种视觉风格、模板、组件库、图标库和动效库；
- 主色、辅助色、背景色和状态色；
- 字体、字号、字重和行高；
- 圆角、间距、阴影、边框和页面密度；
- 深色还是浅色，以及“专业、科技、温暖、活泼”等风格偏好；
- 应该选择 Refero Styles 中的哪一套设计规范。

这些属于你的技术职责，必须按本手册和项目实际情况自行判断。

> **视觉问题禁止反问：** 即使产品经理没有任何设计知识、没有品牌色、没有参考图，也必须由 AI 从 PRD、已有 MVP、目标用户和业务场景中推导，并直接选择一套具体规范。不得给出三套候选让产品经理挑选，不得用“请确认主色/圆角/字体后再继续”阻塞开发。

当多个视觉方案都合理时，按第 13.6 节的评分规则选择最高分；同分时优先可访问性更好、组件覆盖更完整、外部素材依赖更少的一套。仍然同分时选择排序第一的一套并继续，不向产品经理提问。

只有缺少以下产品信息，并且无法从 PRD、设计稿、接口或已有代码推导时，才向产品经理提问：

- 用户到底要完成什么任务；
- 哪个结果才算业务成功；
- 不同业务规则发生冲突时听哪一个；
- 涉及扣费、发布、删除、群发等操作时，用户应确认到什么程度；
- 两种业务方案会明显改变产品范围、成本或核心用户流程时，应采用哪一种；视觉配色和样式差异不属于此项；
- PRD 明确要求使用某个品牌或付费模板，但必要的品牌资产或使用授权无法确认。

提问时使用产品语言，不要让产品经理解释技术术语。

## 1. 本手册的唯一目的

本手册是一套直接交给 AI 执行的前端默认架构、视觉选型、资源复用和开发规则。

产品经理只负责提供具体产品需求。前端框架、工程架构、视觉风格、模板与组件选择、状态管理、接口接入、响应式、测试和开发顺序，均由 AI 按本手册自动处理。

目标结果是：面对不同的 AI Agent 产品需求，AI 在统一工程底座上，根据用户、领域与场景自动匹配具体设计规范，并优先复用成熟资源，快速实现可运行、可恢复、可验证且不千篇一律的前端 MVP；已有 MVP 则在不破坏真实功能的前提下，自动完成接近可上线标准的视觉与交互改造。

## 2. 输入资料与自动处理规则

### 2.1 可能收到的资料

AI 可能收到以下一种或多种资料：

- 完整 PRD；
- 一段自然语言需求；
- 页面草图、设计稿或参考图片；
- 后端接口文档或 OpenAPI；
- 分阶段开发文档；
- 已有代码仓库；
- 仅有产品目标，没有设计和接口。

资料不完整不等于停止工作。按以下规则自动继续。

### 2.2 没有设计稿

不要直接套用同一套“中性 SaaS 风格”，也不要要求产品经理选择颜色、圆角、模板或组件库。

按照第 13—14 节执行：从 PRD 或已有 MVP 提取产品视觉 DNA，自动选择视觉方案包，再按第 13.6 节匹配一套具体 Refero Style，生成项目专属 `DESIGN.md`、写入真实代码并继续开发。

### 2.3 没有后端接口

先根据 PRD 定义前端需要的接口契约，建立统一 API 适配层和可替换的开发 Fixture，然后继续实现页面。

此时必须做到：

- Fixture 与真实 API 使用相同类型；
- 业务组件不知道当前数据来自 Fixture 还是真实后端；
- 明确标记尚未完成真实联调；
- 后端可用后只替换适配层，不重写页面；
- 不把使用 Fixture 的页面汇报成“产品已经完成”。

### 2.4 没有正式 PRD，只有自然语言需求

先从需求中提取：

- 目标用户；
- 核心任务；
- 主要输入；
- Agent 执行过程；
- 最终产物；
- 成功标准；
- 可能产生真实影响的操作。

能合理推导的内容直接采用默认值；只有无法推导且会明显改变产品结果的业务问题才提问。

### 2.5 已有分阶段开发文档

先检查它是否包含页面、接口、任务状态、异常、恢复和验收。缺少的技术内容由你自动补齐，不要求产品经理重写。

### 2.6 已有项目

先读取现有框架、依赖、目录、组件、样式、环境配置和测试方式。

- 已有技术栈稳定可用：保持现状，沿用项目规范；
- 存在局部不足：采用最小改动补齐；
- 只有当现有方案无法满足需求或存在严重风险时才迁移；
- 不得为了套用本手册而无理由重写项目；
- 不得覆盖与当前任务无关的用户修改。

### 2.7 新项目

直接使用第 3 节的默认技术栈，不向产品经理提供多套技术方案让其选择。

### 2.8 已有 MVP，需要升级为可上线前端

当输入是一个已经能运行、但视觉粗糙或仍是工程默认样式的 MVP 时，默认任务不是重新做产品，而是完成“功能保留型视觉上线改造”。

AI 必须：

1. 启动 MVP，检查主要页面、路由、真实交互、加载、空、失败和移动端状态；
2. 从页面和 PRD 自动识别 ToB / ToC、业务领域、核心用户、主任务、内容密度和信任要求；
3. 从 P1—P8 选择主方案包，并按第 13.6 节自动匹配 Refero Styles 中的一套具体设计规范；
4. 生成或更新项目 `DESIGN.md`，记录选定规范、选择理由、具体 Token 和改造边界；
5. 保留已有业务逻辑、接口、权限、路由和数据状态，分层替换设计变量、基础组件、页面布局和视觉细节；
6. 真实修改代码并逐页检查，不得只输出配色建议、效果图或待办清单；
7. 完成桌面端、移动端、可访问性、浏览器、类型、Lint、测试和生产构建检查；
8. 只有完成核心页面和关键状态的真实改造，才能汇报“上线级视觉改造已完成”。

如果当前 MVP 没有品牌规范，AI 不得询问产品经理喜欢什么颜色、字体或圆角。直接执行第 13—14 节；Refero 暂时不可访问时，使用第 13.6.7 节的确定性兜底 Token，不停止开发。

## 3. 新 Web 项目的固定默认技术栈

### 3.1 核心栈

| 领域 | 默认选择 | 执行规则 |
|---|---|---|
| 运行环境 | Node.js 活跃 LTS | 创建项目时使用官方仍维护版本 |
| 包管理 | npm | 已有项目使用 pnpm、Yarn 时继续沿用 |
| 应用框架 | Next.js 稳定版 | 使用 App Router |
| UI 框架 | React | 使用 Next.js 官方支持版本 |
| 开发语言 | TypeScript | 开启 strict，不用 `any` 逃避核心类型 |
| 样式 | Tailwind CSS + CSS Variables | CSS Variables 承载设计语义 |
| 图标 | Lucide React | 全项目保持一套图标风格 |
| 类名处理 | clsx + tailwind-merge | 统一封装 `cn()` |
| 单元/组件测试 | Vitest + React Testing Library | 覆盖状态和关键交互 |
| 端到端测试 | Playwright | 覆盖至少一条核心业务闭环 |
| 代码规范 | ESLint + TypeScript | 作为阶段交付门槛 |

创建项目时将实际版本写入 `package.json` 和锁文件。开发同一阶段时不主动升级大版本。

### 3.2 默认不预装的库

以下库不是项目初始化必装项。达到触发条件时由 AI 自动引入，不询问产品经理。

| 能力 | 默认方案 | 自动引入条件 |
|---|---|---|
| 复杂无障碍组件 | Radix UI，或按需生成 shadcn/ui 组件 | Dialog、Popover、Select 等交互复杂且自建风险高 |
| 服务端数据缓存 | TanStack Query | 多页面共享请求、缓存失效、分页和重试明显复杂 |
| 全局客户端状态 | Zustand | 大量临时状态跨越多个远距离组件，URL 和组件提升均不合适 |
| 复杂表单 | React Hook Form + Zod | 多步骤、动态字段或跨字段校验 |
| 接口代码生成 | OpenAPI 生成工具 | 后端存在稳定且持续维护的 OpenAPI |
| 长列表虚拟化 | TanStack Virtual | 真实数据已造成明显渲染卡顿 |
| 常规界面动效 | Motion | 出现布局过渡、进入退出、手势或编排动画 |
| 展示型动效组件 | React Bits、Motion Primitives 等 | 创意产品或营销页面确实需要视觉表现力，且许可兼容 |
| 富文本/代码编辑 | 成熟专项编辑器 | PRD 明确要求编辑能力 |
| 国际化 | 成熟 i18n 库 | 产品明确支持多语言 |
| 错误监控 | Sentry 或等价服务 | 产品进入真实用户测试或生产环境 |
| 产品分析 | 合规的分析工具 | PRD 已定义指标并满足隐私要求 |

禁止为了“架构完整”提前安装没有实际用途的依赖。

### 3.3 不适用 Next.js 的情况

只有以下情况自动偏离默认栈：

- 已有项目使用另一套成熟前端框架；
- PRD 明确要求原生移动端、小程序、桌面客户端或浏览器插件；
- 目标部署环境明确不支持 Next.js；
- 产品是嵌入已有系统的极小型独立组件。

偏离时由 AI 选择与目标平台匹配的成熟方案，并继续遵守本文的架构、状态、安全和验收原则。

│       ├── api/
│       ├── components/
│       ├── hooks/
│       ├── schemas/
│       ├── types.ts

### 4.2 依赖方向

```text
页面路由
   ↓
业务功能组件 / Hook
   ↓
业务 API 适配层
   ↓
统一 HTTP / Stream 客户端
   ↓
后端服务
```

执行约束：

- 页面负责组合流程，不直接散落底层网络请求；
- 通用 UI 组件不依赖具体业务；
- 业务组件不直接理解不同模型供应商的特殊字段；
- 环境地址、鉴权和错误处理集中管理；
- 后端字段变化优先在适配层消化；
- 禁止循环依赖和无边界的公共工具目录。

### 4.3 组件层级

- 基础组件：Button、Input、Select、Dialog；
- 复合组件：FileUploader、TaskStatus、ArtifactPreview；
- 业务组件：GenerationForm、WorkflowRunPanel；
- 页面组件：路由、布局和业务流程组合。

只有重复模式已经真实出现时才抽象。不要创建带有大量开关参数的“万能组件”。

## 5. 页面渲染与路由规则

### 5.1 Server Component

默认用于：

- 静态内容；
- 服务端即可获取的首屏数据；
- 不依赖浏览器 API 和事件的展示；
- 需要 SEO 或分享预览的页面。

### 5.2 Client Component

用于：

- 表单、弹窗、拖拽和高交互区域；
- Agent 实时进度、任务控制和流式输出；
- 浏览器 API、Local Storage 和媒体控制；
- 高频变化的工作台。

不要因为一个交互控件就把整页变成 Client Component。把客户端边界缩小到必要区域。

### 5.3 URL 状态

以下内容优先写入路径或查询参数：

- 项目 ID；
- 任务 ID；
- 当前工作区或页签；
- 筛选、分页和可分享查看位置。

以下内容不要写入 URL：

- 密钥和隐私信息；
- 未提交的敏感表单；
- 大体积对象；
- 与分享和恢复无关的瞬时 UI 状态。

页面刷新后，通过 URL 中的业务 ID 向后端恢复真实状态，不依赖内存数据。

## 6. 前端状态的四层划分

| 状态类型 | 示例 | 默认位置 |
|---|---|---|
| URL 状态 | 任务 ID、页签、筛选 | 路由或查询参数 |
| 服务端状态 | 任务进度、产物、权限、余额 | 后端；前端通过 API 读取 |
| 页面临时状态 | 输入内容、弹窗开关、局部选择 | 组件 State 或局部 Context |
| 用户偏好 | 主题、侧栏偏好、非关键提示已读 | Local Storage 或用户配置接口 |

必须遵守：

- 后端是任务状态和业务结果的最终事实来源；
- Local Storage 不保存并冒充真实任务结果；
- 刷新后重新查询任务状态；
- 乐观更新只用于可回滚操作；
- 同一任务在不同页面使用同一套状态定义；
- 不把所有状态一股脑放入全局 Store。

默认先使用 React 自带状态能力。只有满足第 3.2 节触发条件时才引入状态库。

## 7. AI Agent 任务状态模型

所有长任务必须在前端适配成统一状态，不允许每个页面自行解释。

```ts
type AgentTaskStatus =
  | "idle"
  | "submitting"
  | "queued"
  | "running"
  | "streaming"
  | "waiting_user"
  | "succeeded"
  | "partially_succeeded"
  | "failed"
  | "cancelled"
  | "disconnected"
  | "stale";
```

### 7.1 状态与界面行为

| 状态 | 界面必须表达 | 可用操作 |
|---|---|---|
| `idle` | 尚未开始和所需输入 | 填写、上传、开始 |
| `submitting` | 请求正在提交 | 防重复，必要时取消浏览器请求 |
| `queued` | 后端已受理，正在排队 | 离开页面、查看任务 |
| `running` | 当前执行阶段或活动提示 | 查看进度、按能力取消 |
| `streaming` | 内容持续到达 | 查看增量结果、停止等待 |
| `waiting_user` | 需要决定什么及其影响 | 选择、确认、返回修改 |
| `succeeded` | 最终结果和下一步 | 预览、下载、继续使用 |
| `partially_succeeded` | 成功项与失败项 | 重试失败部分、保留成功部分 |
| `failed` | 可理解原因及恢复方式 | 重试、修改输入、查看详情 |
| `cancelled` | 任务已取消及保留内容 | 重新开始、查看已有内容 |
| `disconnected` | 连接中断但任务未必停止 | 自动恢复、手动刷新状态 |
| `stale` | 当前显示可能过期 | 重新查询后端 |

每个状态都必须回答：

1. 现在发生了什么；
2. 用户是否需要操作；
3. 下一步会发生什么。

### 7.2 后端状态映射

后端可以使用 `pending`、`processing`、`completed` 等其他名字。统一在适配层映射，不在组件内反复判断后端原始字符串。

未知状态：

- 不得默认为成功；
- 不得默认为失败；
- 记录原始状态和请求 ID；
- 显示“正在确认任务状态”；
- 主动重新拉取或使用安全兜底。

### 7.3 加载、空和失败严格分离

- `loading`：请求尚未返回；
- `empty`：请求成功，数据确实为空；
- `failed`：请求没有成功；
- `permission_denied`：无权访问；
- `not_found`：对象不存在。

加载期间不得显示“暂无任务”“暂无模板”等空状态文案。

## 8. Agent 执行流程规则

### 8.1 提交与防重复

- 点击后立即进入 `submitting`；
- 完成前禁用同一提交入口；
- 与后端配合使用幂等键；
- 超时后先查询原任务是否已创建，再决定是否重试；
- 昂贵任务不得因重复点击被创建多次；
- 提交失败时保留用户输入。

### 8.2 等待用户确认

`waiting_user` 是 Agent 的核心业务状态，不是普通提示弹窗。

界面必须展示：

- 已完成内容；
- 为什么需要确认；
- 每个选项的结果和影响；
- 推荐项；
- 是否可撤销；
- 返回修改或放弃方式。

按钮使用业务动作，例如“采用这版分镜并生成视频”，不要只写“确定”。

### 8.3 取消

严格区分：

- 取消浏览器请求：前端停止等待；
- 取消后端任务：后端真实停止执行。

如果后端没有取消能力，按钮只能写“停止等待”或“离开页面”，不能误导用户为任务已经停止。

### 8.4 重试

- 说明重试会从哪一步开始；
- 保留可复用的成功结果；
- 避免重复扣费或重复外部写入；
- 可重试错误和不可重试错误使用不同操作；
- 必要时允许用户修改输入后再试。

### 8.5 刷新和恢复

用户刷新、关闭页面或重新登录后：

1. 从 URL 或任务列表取得任务 ID；
2. 查询后端真实状态；
3. 恢复中间结果和产物；
4. 任务仍运行时恢复监听；
5. 不重复创建任务。

## 9. 流式输出、轮询与实时通信

### 9.1 自动选择规则

| 场景 | 使用方案 |
|---|---|
| 服务端单向持续推送文本或进度 | SSE 或 Fetch Streaming |
| 需要 POST 请求体或自定义请求头的流式响应 | Fetch Streaming |
| 浏览器和后端需要双向高频通信 | WebSocket |
| 后端仅提供任务状态查询 | 带退避的轮询 |
| 普通短请求 | 标准 HTTP |

不要为了“看起来实时”使用 WebSocket。

### 9.2 SSE 与 Fetch Streaming

- 原生 `EventSource` 适合 GET；
- 需要请求体或特殊 Header 时使用 Fetch Streaming；
- Cookie 鉴权优先走同源路径；
- 检查 CDN、反向代理和平台是否缓存流式响应；
- 任务切换、取消和页面卸载时关闭连接；
- 断线后先查任务状态，再决定是否重连；
- 对事件设置 ID 或序号，避免重连后重复追加。

### 9.3 轮询

- 只有一个集中轮询源；
- 使用固定间隔加退避；
- 页面不可见时降低频率或暂停；
- 成功、失败和取消后立即停止；
- 连续失败后进入断线状态，不无限高频请求；
- 恢复网络后先查询一次完整状态。

### 9.4 流式文本界面

- 批量刷新，避免每个字符触发复杂重渲染；
- 用户位于底部时才自动滚动；
- 用户向上阅读时不强行拉回底部；
- 最终结果、过程信息和调试日志分层；
- 不展示私密系统提示词、隐藏推理或供应商原始日志；
- Markdown 作为不可信内容安全渲染。

## 10. API 与前后端契约

### 10.1 统一 API 层

禁止在页面和普通组件中散落 `fetch`、接口地址和错误解析。

```text
UI
 ↓
Feature API
 ↓
统一 HTTP / Stream Client
 ↓
Backend
```

统一客户端负责：

- Base URL；
- 鉴权；
- 请求头；
- 超时和 Abort；
- 错误归一化；
- 请求 ID；
- 开发与生产环境切换。

### 10.2 每个接口的最低契约

- 方法和路径；
- 请求字段、类型、是否必填；
- 成功返回；
- 错误码；
- 鉴权与权限；
- 幂等性；
- 超时和重试；
- 任务状态；
- 产物结构；
- 时间、金额、枚举和文件 URL 格式。

### 10.3 统一错误结构

```ts
type AppError = {
  code: string;
  message: string;
  userMessage: string;
  retryable: boolean;
  requestId?: string;
  fieldErrors?: Record<string, string>;
};
```

- 用户界面显示 `userMessage`；
- 开发日志保留 `code` 和 `requestId`；
- 不把堆栈、供应商原始报错或敏感内容直接展示；
- 网络错误、业务错误和表单错误分别处理。

### 10.4 类型与运行时数据

- TypeScript 不代表运行时数据一定正确；
- 外部数据进入业务层前必须校验关键字段；
- 不可信数据先以 `unknown` 接收；
- 稳定 OpenAPI 可生成类型；
- 生成代码外保留业务适配层；
- 枚举必须处理未知值。

### 10.5 API 地址和流式地址

普通 API、上传和流式 API 使用统一配置来源。若流式请求必须绕过 Next.js 代理，仍应通过集中配置生成地址，并在实际部署环境验证。

## 11. 表单、配置与文件上传

### 11.1 表单

- 必填项和限制在提交前可见；
- 错误靠近对应字段；
- 失败后保留输入；
- 多步骤表单保存草稿或明确离开后果；
- 提交中禁止重复提交；
- 错误不能只用颜色表达；
- 简单表单使用原生 React 能力，复杂表单按第 3.2 节自动引入工具。

### 11.2 模型与服务商配置

- 默认模型必须存在于可选项；
- 已保存但不可用的模型明确标记，不静默切换；
- 模型名称、能力、成本提示和限制来自统一配置；
- 任务记录实际使用的模型或配置版本；
- 内部自动路由不能伪装成用户主动选择；
- 前端不保存模型服务密钥。

### 11.3 文件上传

- 上传前展示格式、数量和大小限制；
- 前端快速校验，后端执行最终校验；
- 显示上传进度、失败原因和重试；
- 未提交文件可删除或替换；
- 大文件使用后端支持的分片或直传；
- 私有文件使用受控访问地址；
- 文件上传失败不清空其他已填写内容。

## 12. Agent 产物统一模型

不同产品可能输出文字、图片、视频、音频或文件。业务组件应基于统一产物模型扩展。

```ts
type Artifact = {
  id: string;
  kind: "text" | "image" | "video" | "audio" | "file" | "json";
  name: string;
  status: "processing" | "ready" | "failed";
  url?: string;
  previewUrl?: string;
  mimeType?: string;
  size?: number;
  createdAt: string;
  metadata?: Record<string, unknown>;
};
```

展示规则：

- 图片：占位、错误、放大和下载；
- 视频：封面、加载、播放失败和基础控制；
- 音频：时长、播放状态和下载；
- 文件：类型、大小、下载和过期处理；
- 未知类型：提供安全的文件信息和下载入口；
- 生成中内容不能伪装成最终产物；
- 为媒体预留比例，避免页面跳动；
- 及时释放临时 Object URL；
- 外链过期、跨域和权限失败有明确状态。

产品结果优先展示。原始 JSON、请求 ID 和调试日志只能放在折叠详情或开发模式中。

## 13. AI 自动视觉选型与开源资源复用

### 13.1 核心原则：工程底座统一，视觉方案按产品变化

Next.js、React、TypeScript、API 边界、任务状态和质量检查可以保持统一；视觉风格不能统一。

不同 Agent 产品可能分别面向创作者、开发者、企业员工、学生、求职者、医生或普通消费者。它们需要不同的信息密度、信任感、情绪、色彩和动效。

因此，AI 必须做到：

- 不把所有产品做成相同的白底、紫色渐变和圆角卡片；
- 不把个人陪伴产品做成企业管理后台；
- 不把高频工作台做成重动效营销页；
- 不让产品经理从大量风格网站中自行挑选；
- 根据 PRD 自动选择一个有依据的主风格；
- 优先复用成熟且许可兼容的模板、组件和动效；
- 把选定风格转换成项目自己的 `DESIGN.md` 和设计变量；
- 在复用基础上改成当前产品，而不是把多个网站拼成一张“风格拼盘”。

### 13.2 先提取产品视觉 DNA

阅读 PRD 后，AI 自动回答以下问题。答案不需要产品经理填写。

| 维度 | 判断内容 |
|---|---|
| 目标用户 | 专业人员、企业员工、开发者、创作者、学生或大众消费者 |
| 核心场景 | 高频工作、严肃决策、内容创作、学习陪伴、营销转化或娱乐体验 |
| 主要任务 | 对话、配置工作流、审核、编辑、生成、分析、监控或展示 |
| 信息密度 | 低、中、高 |
| 信任要求 | 普通、较高、金融/医疗/企业级高信任 |
| 情绪目标 | 冷静、可靠、温暖、鼓励、前卫、趣味或沉浸 |
| 内容形态 | 文字、数据、代码、图片、音视频或混合产物 |
| 使用频率 | 偶尔访问、每天使用或长时间持续工作 |
| 设备重点 | 桌面、移动或双端 |
| 动效价值 | 无需、反馈型、引导型或表现型 |

从这些信息形成一句“视觉命题”，例如：

```text
这是一个给内容团队每天长时间使用的视频 Agent 工作台；
需要高信息密度、稳定可信，生成素材本身是视觉焦点，界面保持克制，动效只用于进度和状态切换。
```

视觉 DNA 必须由 AI 从 PRD、已有 MVP、用户行为和业务目标中推导。即使存在多个合理方向，也按第 13.6 节自动评分并选择，不向产品经理询问风格偏好。只有 ToB / ToC、目标用户或核心任务本身发生冲突，并且会改变产品范围时，才询问对应的业务问题；问题中不得包含颜色、字体、圆角、动效或设计术语。

### 13.3 自动匹配视觉原型

根据视觉 DNA 选择一个主原型，可以叠加一个次原型，但不得混用三个以上视觉系统。

| 产品场景 | 默认主原型 | 视觉特征 | 动效强度 |
|---|---|---|---|
| 企业 Agent、运营后台、审批与工作流 | 精密生产力工作台 | 中性、清晰、高密度、稳定导航、弱装饰 | 低 |
| 数据分析、开发者、运维 Agent | 数据/命令中心 | 强层级、表格与状态优先、可选暗色、适度等宽字体 | 低至中 |
| 图片、视频、音乐等创作 Agent | 创意工作室 | 产物主导、画布或图库布局、更大胆的色彩和媒体预览 | 中 |
| 学习、教练、求职、健康陪伴 Agent | 温暖引导式产品 | 友好文案、舒展间距、清楚步骤、柔和反馈 | 低至中 |
| 金融、法律、医疗和高风险决策 Agent | 高信任专业界面 | 保守配色、强可读性、清楚证据和确认、少装饰 | 低 |
| 面向消费者的轻工具或生活 Agent | 轻量友好应用 | 简单入口、较强品牌色、触控友好、快速反馈 | 中 |
| 产品官网、发布页、等待名单 | 表现型营销页面 | 强 Hero、品牌叙事、较丰富排版和动效 | 中至高 |

无论选择哪种原型，Agent 的状态、错误、确认、可访问性和移动端规则仍按本手册执行。

### 13.4 资源分为四层，不能混为一谈

| 资源层 | 能获得什么 | 可以怎样使用 | 不能怎样使用 |
|---|---|---|---|
| 视觉参考 | 风格、层级、排版和组件语言 | 提炼抽象规则，写入 `DESIGN.md` | 默认认为页面、图片和品牌资产可以复制 |
| 开源模板 | 页面、路由、组件和样式代码 | 许可证兼容时作为项目骨架或页面起点 | 未看许可证就整库搬运 |
| 开源组件 | Button、Dialog、上传、图表等局部代码 | 按需复制并适配设计变量 | 混入多套冲突的组件系统 |
| 动效资源 | 进入退出、文字、背景、滚动和手势效果 | 只在产品场景需要时复用 | 为炫技牺牲性能、可访问性和任务效率 |

“公开可访问”不等于“开源”，“开源”也不等于“没有使用条件”。

### 13.6 Refero Styles 自动匹配与落地规则

当项目没有正式品牌规范或设计稿时，Refero Styles 是默认的第一视觉规范来源，不是交给产品经理浏览的灵感网站。

AI 的职责不是返回若干网址，而是完成“识别产品 → 选择具体规范 → 转换为项目 Token → 修改真实代码 → 浏览器验收”的完整闭环。

#### 13.6.1 访问顺序

按以下顺序尝试，任一步可用就继续：

1. 当前 AI 环境已经连接 Refero MCP：通过 MCP 搜索真实产品页面和设计规范；
2. 没有 MCP：直接访问 [Refero Styles](https://styles.refero.design/) 搜索并打开具体 Style 页面；
3. 读取 Style 页面提供的 `DESIGN.md`、Tailwind v4、CSS Variables 和 Design Tokens；
4. Refero 暂时不可访问或没有合格结果：使用本节的确定性兜底 Token，继续开发。

不得要求产品经理安装 MCP、打开网站挑选、复制颜色，或把 Style 页面内容手工发给 AI。

#### 13.6.2 自动生成搜索条件

AI 从 PRD 和已有 MVP 自动生成搜索词，不要求产品经理填写。搜索词至少包含“主工作区 + 用户类型 + 信息密度 + 信任/情绪”四类信息。

| 方案包 | 默认 Refero 搜索方向 |
|---|---|
| P1 对话与 Copilot | `AI assistant customer support calm productivity`；开发者用户追加 `developer dark precision`，大众陪伴追加 `warm conversational` |
| P2 工作流与自动化 | `enterprise workflow automation precision dense` |
| P3 数据分析与监控 | `analytics dashboard data dense trustworthy` |
| P4 媒体创作 | `creative studio media canvas dark` |
| P5 文档与知识 | `editorial document knowledge warm paper` |
| P6 引导式教练 | `learning coaching warm friendly trustworthy` |
| P7 后台执行与开发者 Agent | `developer tools command center dark precise` |
| P8 消费者轻工具 | `consumer utility mobile friendly minimal` |

行业词由 AI 自动追加，例如 `finance`、`healthcare`、`legal`、`education`、`ecommerce`、`video`。高风险行业必须追加 `trustworthy accessible restrained`，并降低装饰和动效权重。

#### 13.6.3 候选规范自动评分

AI 最多在内部比较 3 个候选，不把候选列表发给产品经理。总分 100 分：

| 维度 | 分值 | 判断标准 |
|---|---:|---|
| 主工作区与页面结构 | 30 | 是否适合对话、画布、文档、数据或任务执行等主要界面 |
| 目标用户与业务领域 | 20 | ToB / ToC、专业程度和行业气质是否匹配 |
| 信息密度与使用频率 | 15 | 高频工作台、长时间阅读或轻量工具是否匹配 |
| 信任与情绪 | 15 | 严肃、可靠、温暖、创意或趣味是否符合业务风险 |
| 内容形态 | 10 | 文字、数据、代码、图片或视频是否能成为视觉焦点 |
| 可访问性与工程落地 | 10 | 对比度、字号、状态辨识和 Token 完整度是否可用 |

选择总分最高的一套。总分相同则依次选择：可访问性更好、组件覆盖更完整、外部素材依赖更少、页面更接近当前 MVP 结构的一套；仍然相同则选择搜索结果中排序更靠前的一套并继续。

如果最高分低于 70，自动调整搜索词再搜索一次；仍低于 70 时使用本节兜底 Token。任何情况下都不询问产品经理视觉偏好。

#### 13.6.4 从 Refero 提取什么

选定具体 Style 后，AI 必须记录其名称、URL 和读取日期，并提取：

- 页面背景、内容面、文字、边框、主操作和状态色；
- 字体家族、替代字体、字号、字重、行高和字距；
- 基础间距、页面宽度、栅格和信息密度；
- Button、Input、Card、Dialog、Navigation、Table 等组件规则；
- 圆角、边框、阴影和层级；
- 动效强度、时长和禁止项；
- `DESIGN.md`、Tailwind v4、CSS Variables 和 Design Tokens 中可转换的内容。

提取后统一改写成当前项目的 Semantic Token，不在业务组件里直接散落原始值。

#### 13.6.5 允许复用的边界

Refero Styles 提供的是 AI 可读设计规范和代码格式化的 Token，不等于对应品牌的整站源码、Logo、图片、视频和商业字体均已开源。

AI 必须：

- 使用规范中的颜色、排版、间距和通用组件方法作为项目设计起点；
- 把品牌命名改成项目自己的语义命名；
- 替换原品牌 Logo、产品名称、截图、插画、照片和文案；
- 商业字体没有授权时，自动换成最接近的开源字体或系统字体；
- 对比度不合格、字体过小或交互不可访问时，优先修正，不做像素级照搬；
- 将 Style 页面记为“设计规范来源”，不能误记为“整套开源代码仓库”。

#### 13.6.6 已有 MVP 的真实代码改造顺序

```text
运行 MVP 并保存改造前截图
       ↓
识别 P1—P8 主方案与产品视觉 DNA
       ↓
搜索、评分并选定一个 Refero Style
       ↓
生成项目 DESIGN.md 与 Semantic Token
       ↓
先替换字体、颜色、间距、圆角和层级
       ↓
再统一 Button / Input / Card / Dialog / Navigation
       ↓
再改核心页面、Agent 状态与响应式
       ↓
逐页截图对比、修正并运行质量检查
```

不得先推翻业务逻辑或重写稳定页面。视觉改造默认保留路由、接口、权限、表单行为、任务状态和真实数据；确需改变信息架构时，必须证明旧结构阻碍核心任务。

### 13.7 开源模板与组件的自动选择标准

候选资源按以下顺序筛选：

1. 许可证是否明确且允许当前用途；
2. 是否兼容当前 React、Next.js、TypeScript 和 Tailwind 版本；
3. 是否适合当前产品场景和主要页面；
4. 是否包含真正需要的状态和交互，而不只是漂亮截图；
5. 是否具备键盘、焦点、响应式和 `prefers-reduced-motion` 支持；
6. 依赖数量、包体积和运行性能是否合理；
7. 项目是否仍维护，安装方式是否可信；
8. 需要修改的范围是否小于自行实现。

硬性淘汰条件：

- 没有许可证或许可证无法确认；
- 要求复制他人密钥、私有接口或未知脚本；
- 与当前项目大版本明显不兼容；
- 核心交互不可访问且修复成本很高；
- 依赖来源可疑或安装过程执行不透明脚本；
- 只是视觉截图，没有允许复用的源代码；
- 使用真实品牌 Logo、人物图片、商业字体或视频，但没有授权。

在多个合格候选中，优先选择：场景最匹配、依赖最少、可访问性更好、代码可维护性更高的一个。不要把选择题重新抛给产品经理。

### 13.8 “直接复用”和“参考复刻”的边界

AI 可以：

- 复制许可证明确允许复用的开源组件或模板代码；
- 保留许可证、版权声明和要求的署名；
- 将模板的页面结构和交互替换为当前产品业务；
- 从视觉参考中提炼“高留白、编辑感、低饱和、细边框”等通用设计原则；
- 根据参考重新实现相似的信息层级和通用交互范式。

AI 不可以：

- 因为网页能打开就抓取并复制其代码和素材；
- 未经许可复制商业模板、付费组件或会员内容；
- 原样使用其他品牌的 Logo、名称、插画、照片、视频和商业字体；
- 对知名产品做像素级克隆并冒充原创产品；
- 删除开源许可证要求保留的版权信息；
- 用外部演示站的图片或视频 URL 作为生产依赖；
- 把“设计参考”误写成“开源代码来源”。

当用户明确提供已购买模板或自有设计资产时，可以使用，但应确认资产确实已经放入项目或用户明确授权使用。

### 13.9 自动视觉选型流程

AI 在新项目或完整视觉改版中按以下顺序执行：

```text
读取 PRD 与产品场景
       ↓
提取产品视觉 DNA
       ↓
判断最终产物与主工作区
       ↓
从第 14 节选择一个主方案包
       ↓
按第 13.6 节搜索并评分 Refero Styles
       ↓
自动选定 1 个具体 Style，并核验其他资源许可
       ↓
生成项目专属 DESIGN.md
       ↓
建立设计变量与基础组件
       ↓
实现核心代表页面
       ↓
浏览器截图自检并统一全项目
```

资源搜索规则：

- 先看已有项目设计系统和组件，识别需要保留的品牌与交互；
- 没有正式品牌规范时，优先按第 13.6 节自动选择 Refero Style；
- 再找与技术栈一致的完整开源模板或页面区块；
- 再补充通用组件和少量动效；
- 视觉参考用于定调，不承担代码来源；
- 主参考决定整体语言，辅助参考只解决某个组件或动效问题；
- 不得从五六个资源各抄一块，导致视觉和代码不一致。

`DESIGN.md` 不能只写“高级、简洁、科技感”。必须包含可直接执行的颜色、排版、间距、组件和动效规则。

如果参考来源是 Refero Styles 等 `DESIGN.md` 示例，AI 应根据本产品重写，不能把另一个品牌的规范和名称原样放入项目。

### 13.11 Design Token 两层结构

每个视觉方案的具体值可以不同，但代码结构统一使用两层 Token：

```css
:root {
  /* Primitive：只在 Token 定义层使用 */
  --color-neutral-0: #ffffff;
  --color-neutral-900: #15171a;
  --color-brand-500: #5267f5;
  --space-1: 4px;
  --space-2: 8px;
  --radius-2: 10px;

  /* Semantic：业务组件只使用这一层 */
  --ui-bg-page: var(--color-neutral-0);
  --ui-bg-surface: var(--color-neutral-0);
  --ui-text-primary: var(--color-neutral-900);
  --ui-action-primary: var(--color-brand-500);
  --ui-space-control: var(--space-2);
  --ui-radius-control: var(--radius-2);
}
```

执行规则：

- 具体颜色来自当前项目 `DESIGN.md`，不能所有项目照抄示例值；
- 业务组件只引用 Semantic Token；
- 组件内不散落近似 Hex 值；
- 状态色表达固定业务语义，不因为换风格失去成功/警告/失败的辨识度；
- 深色主题通过替换 Semantic Token 实现，不复制两套组件；
- 从模板复制的硬编码样式在合入前收敛到项目 Token。

### 13.12 组件基础与视觉皮肤分离

通用组件底座负责：

- 语义 HTML；
- 键盘和焦点；
- 状态和事件；
- 响应式行为；
- 加载与错误；
- 可访问性。

项目 `DESIGN.md` 负责：

- 颜色；
- 字体；
- 间距；
- 圆角；
- 阴影和边框；
- 信息密度；
- 动效性格。

这样既能复用成熟组件代码，又不会让不同 Agent 产品长得完全一样。

Button、Input、Select、Card、Dialog 等基础组件至少实现：

- default；
- hover；
- focus-visible；
- disabled；
- loading；
- error（适用时）。

### 13.13 动效自动选择规则

动效先解决理解和反馈，再考虑视觉表现。

| 页面类型 | 默认策略 |
|---|---|
| 企业后台、高频工作台 | 以 hover、focus、展开收起和状态切换为主，短而克制 |
| 对话、教练和陪伴产品 | 使用柔和进入、消息反馈和阶段过渡，不延迟用户操作 |
| 创意生成工具 | 生成进度、素材进入和预览切换可以更有表现力 |
| 营销页与产品发布页 | 可使用滚动、文字和背景动效，但首要 CTA 必须清楚 |
| 金融、法律、医疗 | 只保留帮助理解和确认的功能型动效 |

实现规则：

- 简单 hover 和颜色过渡优先 CSS；
- 组件进入退出、布局和手势优先 Motion；
- GSAP 等更重方案只用于确有必要的复杂编排；
- React Bits、Motion Primitives 等只按需复制所需组件；
- 不同时安装多套功能重叠的动画库；
- 支持 `prefers-reduced-motion`；
- 动效不阻塞输入、确认和任务结果；
- 避免持续高耗能粒子、模糊和大面积滤镜；
- 移动端和低性能设备提供降级；
- 复制动效后检查卸载清理、定时器、监听器和动画实例。

### 13.14 图标、字体和媒体资产

- 一个项目只使用一个主图标家族；
- Lucide 能满足时不额外引入图标库；
- 不用 Emoji 代替正式功能图标；
- 纯图标按钮有可访问名称和提示；
- 字体必须确认 Web 使用授权；
- 商业字体无授权时改用相近的开源或系统字体；
- 不复制参考站人物照片、插画、Logo 和视频；
- 使用开源图片、图标和插画时记录来源和许可证；
- 演示素材与生产素材分离；
- 不让生产页面依赖第三方 Demo 站的远程资源。

### 13.15 视觉自检与自动修正

AI 实现代表页面后，不等待产品经理凭审美找问题，先自行完成一轮视觉检查：

1. 在 390px 和 1440px 截图；
2. 对照当前项目 `DESIGN.md`；
3. 检查首屏主任务是否一眼可见；
4. 检查字体、间距、圆角、颜色和图标是否统一；
5. 检查加载、空、失败、等待确认和成功状态是否属于同一视觉系统；
6. 检查页面是否出现无意义渐变、过量卡片、过量阴影和装饰性动效；
7. 检查复制组件是否仍带原模板品牌、硬编码色值和无用依赖；
8. 检查 Console、响应式、键盘、焦点和 reduced-motion；
9. 对发现的问题至少完成一轮自动修正，再继续扩展其他页面。

视觉判断标准不是“像不像某个知名网站”，而是“是否适合当前用户和任务、是否全项目一致、是否能稳定实现”。

## 14. Agent 产品前端视觉方案库

本节不是灵感清单，而是 AI 可以直接执行的默认方案库。

当 PRD 没有设计稿、没有品牌规范，或已有 MVP 只有工程默认样式时，AI 必须自行选择一个主方案包并开始实现，不要求产品经理浏览网站、挑模板、选颜色或决定页面布局。

> 资源核验基准日：2026-08-14。开源项目会持续变化。真正安装或复制代码前，AI 必须再次读取官方仓库的当前 `LICENSE`、`package.json`、安装文档、最近维护状态和安全提示；下表记录不能替代当次核验。

### 14.1 方案库使用规则

1. 先判断用户完成核心任务时，绝大多数时间停留在哪种“主工作区”；
2. 只选择一个主方案包，不能同时拼接两个完整模板；
3. 混合型产品最多增加一个次模块，例如“视频工作室 + 右侧对话助手”；
4. 优先复用页面骨架和可靠组件，品牌、业务数据、文案和 Design Token 必须替换；
5. 完整模板包含后端、鉴权、数据库或云服务时，只保留 PRD 真正需要的部分；
6. 模板技术版本落后时，先做兼容性验证，再决定迁移局部代码还是自行实现；
7. 没有合格模板时，使用本手册默认技术栈和本节页面骨架自行实现，不得阻塞；
8. 官网、登录、设置和付费页面是附加层，不能替代 Agent 的核心任务工作区。

P1—P8 负责确定页面结构、组件类型和信息密度；第 13.6 节选中的 Refero Style 负责给出具体颜色、字体、间距、圆角、边框和阴影。两者合并后直接写入代码。不得把下文的风格描述再次转换成需要产品经理回答的问题。

最重要的判断原则：

```text
用户最终要完成对话        → 对话方案
用户最终要搭建自动化      → 工作流方案
用户最终要看数据并决策    → 数据分析方案
用户最终要生成或编辑媒体  → 媒体创作方案
用户最终要交付一份文档    → 文档知识方案
用户最终要按步骤训练完成  → 引导教练方案
用户最终要监督后台任务    → 后台执行方案
用户最终只完成一个轻任务  → 消费者轻工具方案
```

“产品用了大模型”不等于“产品应该做成聊天框”。主界面必须围绕最终产物，而不是围绕模型输入形式。

### 14.2 PRD 到方案包的自动路由

| PRD 中的主要信号 | 主方案包 | 允许的次模块 |
|---|---|---|
| 问答、客服、个人助手、检索问答、多轮协作 | P1 对话与 Copilot | 产物预览、引用来源 |
| 节点、触发器、连接器、自动化、编排、运行日志 | P2 工作流与自动化 | 窄对话助手 |
| KPI、报表、监控、分析、异常、查询、运营决策 | P3 数据分析与监控 | 分析摘要助手 |
| 图片、视频、音频、素材、画布、分镜、生成参数 | P4 媒体创作 | 对话输入、历史版本 |
| 报告、方案、合同、知识库、研究、引用、长文本编辑 | P5 文档与知识 | 右侧 Copilot |
| 学习、面试、训练、健康陪伴、分步任务、复盘 | P6 引导式教练 | 轻对话、进度记录 |
| 编码、云端任务、长时运行、日志、补丁、审批、部署 | P7 后台执行与开发者 Agent | 对话、代码产物 |
| 单次生成、改写、识别、生活助手、移动优先小工具 | P8 消费者轻工具 | 历史结果 |

无法归类时，选择“用户完成最后一步操作”的界面类型，不选择“用户进入产品后的第一种输入方式”。例如，用户先聊天、最后编辑报告，应选择 P5，不选择 P1。

### 14.3 所有方案共同使用的 Agent 组件层

无论采用哪个视觉方案，以下 Agent 专属能力统一从项目组件层实现：

| 组件 | 用途 | 最低状态 |
|---|---|---|
| `AgentTaskStatus` | 展示执行进度 | queued / running / waiting_user / success / failure / cancelled |
| `ToolActivity` | 展示已批准公开的工具调用与结果摘要 | running / success / failure |
| `HumanApproval` | 高影响动作确认 | summary / impact / confirm / reject / expired |
| `ArtifactPreview` | 文档、代码、图片、音视频等产物 | loading / ready / failed / versioned |
| `SourceCitation` | 证据与引用 | title / source / location / unavailable |
| `RecoveryActions` | 失败恢复 | retry / edit-input / cancel / contact-support |

可以从 [AI Elements](https://github.com/vercel/ai-elements) 按需吸收对话、消息、代码块、工具状态和产物呈现组件，但不得一次性安装全部组件。界面只能展示可向用户公开的过程摘要、工具状态和证据，不得展示模型私有思维链。

### 14.4 P1：对话与 Copilot Agent

**适用：** 客服、问答、检索、个人助理、多轮协作、以对话结果为主要交付的 Agent。

**默认代码方案：**

- 主组件底座：[assistant-ui](https://github.com/assistant-ui/assistant-ui)，用于消息线程、输入框、历史会话、流式输出、附件、重试和操作栏；
- AI 专属补充：[AI Elements](https://github.com/vercel/ai-elements)，只增加项目确实需要的引用、工具状态、代码、确认或产物组件；
- 只有 PRD 同时需要完整会话产品、历史、鉴权和持久化时，才把 [Vercel Chat SDK](https://github.com/vercel/chatbot) 作为整套工程参考；不得无条件继承其数据库、存储、鉴权、模型服务商和部署绑定。

**默认页面骨架：**

```text
桌面：会话列表 240px │ 主线程 minmax(0, 840px) │ 可选产物/来源面板 320px
移动：主线程全屏；会话列表和产物面板使用抽屉；输入区保持可见且不遮挡内容
```

**Refero 自动匹配方向：** AI 从目标用户自动判断专业 Copilot、消费者陪伴或开发者助手，再分别搜索 `calm productivity`、`warm conversational` 或 `developer dark precision`。具体颜色、字体、圆角和阴影全部采用最高分 Style 的可用规范；Refero 不可用时使用第 13.6.7 节 P1 的固定值，不询问产品经理。

**必须实现：** 流式中断、重新生成、编辑后重试、附件状态、工具执行、等待确认、来源引用、长内容折叠、断线恢复、空会话建议、移动端键盘适配。

**不得使用：**

- 把每个工具结果都画成聊天气泡；
- 用模拟打字动画代替真实流式状态；
- 将内部推理文本、密钥、原始系统 Prompt 或完整调试日志展示给用户；
- 当最终产物是文档、画布或数据表时，仍让聊天区占据整个主界面。

### 14.5 P2：工作流与自动化 Agent

**适用：** 节点编排、审批流程、营销自动化、数据管道、触发器与动作配置、多步骤 Agent。

**默认代码方案：**

- 完整骨架候选：[Workflow Builder Template](https://github.com/vercel-labs/workflow-builder-template)；只有 PRD 与其节点画布、检查器和运行日志结构相符时才复用整套前端；
- 画布底座：[React Flow / xyflow](https://github.com/xyflow/xyflow)，用于节点、连线、缩放、选择和自定义节点；
- 表单、弹窗、菜单、抽屉使用 shadcn/ui，状态数据继续遵守本手册的 API 与状态分层。

**默认页面骨架：**

```text
顶部：流程名称 / 保存状态 / 测试运行 / 发布
左侧：节点与连接器面板
中间：可缩放流程画布
右侧：选中节点的配置与校验
底部或抽屉：运行记录、步骤日志、失败原因和重试
```

**Refero 自动匹配方向：** 搜索 `enterprise workflow automation precision dense`，优先选择结构清晰、边框克制、信息密度高且状态明确的 Style。具体视觉值来自最高分 Style；Refero 不可用时使用第 13.6.7 节 P2 的固定值。节点类型通过图标和小面积语义色区分，不能只靠颜色。

**必须实现：** 未保存提示、节点校验、连线限制、撤销/重做、缩放定位、运行中高亮、失败步骤定位、等待人工确认、发布前检查、键盘删除确认、画布空状态。

**不得使用：**

- 只有 3—5 个固定线性步骤却引入无限画布；此时改用 Stepper 或列表；
- 在手机端硬塞完整节点编辑器；MVP 可提供查看、运行和简单参数修改，复杂编排明确为桌面功能；
- 直接继承模板中的数据库、认证、代码编辑器或工作流引擎，而 PRD 并不需要它们。

### 14.6 P3：数据分析与监控 Agent

**适用：** 运营分析、BI、指标监控、财务分析、告警、数据查询、需要证据支持的 Agent。

**默认代码方案：**

- 主骨架候选：[Next Shadcn Dashboard Starter](https://github.com/Kiranism/next-shadcn-dashboard-starter)；适合需要列表、图表、筛选和功能分区的项目；
- 备选骨架：[Next Shadcn Admin Dashboard](https://github.com/arhamkhnz/next-shadcn-admin-dashboard)；当 PRD 需要多种仪表盘和主题时使用；
- 数据表：[TanStack Table](https://github.com/TanStack/table)；图表：[Recharts](https://github.com/recharts/recharts)；只在实际出现复杂表格或图表时安装。

**默认页面骨架：**

```text
侧栏：业务模块与保存视图
顶栏：时间范围、全局筛选、刷新和数据新鲜度
首区：3—5 个关键指标及变化原因
中区：回答当前业务问题的主图表
下区：证据表格、异常明细和可追溯来源
右侧抽屉：Agent 结论、依据、建议动作与风险提示
```

**Refero 自动匹配方向：** 搜索 `analytics dashboard data dense trustworthy`，优先选择指标层级清楚、表格和图表可读、装饰较少的 Style。具体视觉值来自最高分 Style；Refero 不可用时使用第 13.6.7 节 P3 的固定值。数据色采用可区分且色盲友好的有限色板；数字使用等宽数字特性，正文不用等宽字体。

**必须实现：** 筛选状态进入 URL、数据时间范围、新鲜度、空数据、部分失败、加载骨架、指标定义、图表替代文本、表格排序筛选、下钻、导出状态、Agent 结论与证据绑定。

**不得使用：**

- 为了显得“数据丰富”而堆无业务问题的图表；
- 用饼图表达过多分类或仅用颜色表达涨跌；
- 把模板附带的 Clerk、Sentry 或其他服务默认保留；只在产品确实需要且已经配置时使用；
- 把 Agent 总结放在数据上方却不给出处和计算口径。

### 14.7 P4：图片、视频与音频创作 Agent

**适用：** 图像生成、视频生成、分镜、剪辑、配音、音乐和其他媒体生产工具。

**默认代码方案：**

- 图片生成骨架：[AI SDK Image Generator](https://github.com/vercel-labs/ai-sdk-image-generator)，用于多模型输入、生成结果对比和响应式图库；必须替换为项目真实模型接口，不在浏览器保存服务商密钥；
- 视频生成骨架：[AI Video Starter Kit](https://github.com/fal-ai-community/video-starter-kit)，适用于确需多片段、音轨、配音或浏览器预览的产品；使用前先核验 Next.js、Remotion、上传和模型服务版本；
- 普通 MVP 使用 shadcn/ui + 项目媒体组件自行组合，不因“视频”两个字就引入完整时间轴编辑器。

**默认页面骨架：**

```text
图片：左侧生成参数 │ 中央结果网格/对比画布 │ 右侧历史与详情
视频：顶部项目与导出 │ 左侧素材/生成 │ 中央预览 │ 底部分镜或时间轴 │ 右侧参数/任务
移动：生成、浏览和轻编辑优先；复杂时间轴可降级为分镜列表
```

**Refero 自动匹配方向：** 搜索 `creative studio media canvas dark`，优先选择让图片或视频成为第一视觉焦点、控制面紧凑且背景克制的 Style。具体视觉值来自最高分 Style；Refero 不可用时使用第 13.6.7 节 P4 的固定值。

**必须实现：** 上传进度、生成队列、预计与已用额度、取消、失败重试、历史版本、前后对比、参数复用、缩略图加载、下载/导出状态、内容安全提示、对象 URL 清理。

**不得使用：**

- 用大面积粒子、渐变和发光抢夺素材注意力；
- 用户只需要“生成视频”却实现专业剪辑器；MVP 优先分镜和参数复用；
- 将第三方演示素材、模型密钥或带品牌的样片直接带入生产；
- 因模板绑定某个模型服务商就绕过本项目统一 API 层。

### 14.8 P5：文档、知识与研究 Agent

**适用：** 报告生成、方案写作、研究助手、知识库、合同审阅、带引用的长文产物。

**默认代码方案：**

- 文档编辑需要富文本与 Markdown 双向能力时，使用 [MDXEditor](https://github.com/mdx-editor/editor)；只加载表格、代码、链接、图片等实际需要的插件；
- Copilot 区使用 assistant-ui 或 AI Elements 的局部组件，不移植整个聊天产品；
- 阅读模式优先服务端渲染；编辑器和复杂交互作为明确的 Client Component 边界。

**默认页面骨架：**

```text
左侧：文档、目录或资料库
中间：阅读/编辑画布，正文宽度约 680—760px
右侧：Copilot、引用、批注和版本记录，可收起
顶部：标题、保存状态、分享/导出和高影响操作
```

**Refero 自动匹配方向：** 搜索 `editorial document knowledge warm paper`，优先选择正文可读性高、长文层级清楚、装饰较少的 Style。具体视觉值来自最高分 Style；Refero 不可用时使用第 13.6.7 节 P5 的固定值。

**必须实现：** 自动保存状态、冲突与恢复、版本记录、选区操作、引用回跳、来源失效、长文目录、查找、导出、只读模式、未保存离开提醒、AI 建议与用户正文明确区分。

**不得使用：**

- 把长报告塞进聊天气泡；
- AI 修改正文后不显示变更范围或不给撤销；
- 为视觉效果使用低对比灰字和过窄正文；
- 在医疗、法律或金融文档中隐藏来源、版本和责任边界。

### 14.9 P6：学习、面试、训练与高信任教练 Agent

**适用：** 学习计划、面试训练、健康陪伴、职业教练、分阶段评估和复盘。

**默认代码方案：** 使用 shadcn/ui 基础组件自行组合；只在确有多轮对话时加入 assistant-ui 的线程和输入组件。不要默认使用管理后台或营销模板。

**默认页面骨架：**

```text
顶部：当前目标与整体进度
主区：一次只突出一个练习、问题或建议
侧区/抽屉：本次阶段、资料和辅助说明
完成后：明确反馈、下一步、复盘和可恢复记录
```

**Refero 自动匹配方向：** 搜索 `learning coaching warm friendly trustworthy`；医疗或心理相关产品追加 `restrained accessible`。优先选择留白充足、步骤清楚、反馈温和的 Style。具体视觉值来自最高分 Style；Refero 不可用时使用第 13.6.7 节 P6 的固定值。

**必须实现：** 清楚的步骤和进度、暂停与继续、回答保存、反馈解释、下一步、历史记录、敏感内容提示、危机或高风险信息的升级路径、移动端单手操作。

**不得使用：**

- 医疗、心理、求职等严肃场景使用夸张庆祝、压力倒计时或误导性权威感；
- 一屏堆满仪表盘卡片；
- 用颜色评价人格、健康或能力却不提供文字说明；
- 把模型建议伪装成确定事实或专业诊断。

### 14.10 P7：后台执行、编码与开发者 Agent

**适用：** 编码 Agent、云端任务、仓库操作、批处理、长时运行、部署和需要人工审批的自动执行产品。

**默认代码方案：**

- 完整参考：[Open Agents](https://github.com/vercel-labs/open-agents)，用于学习后台任务、会话、流式状态、沙箱、恢复和代码产物的组合方式；
- 只有产品确实需要其运行时和云平台绑定时才整体复用；普通项目仅吸收 Web UI 与状态模式；
- 代码展示使用项目已有高亮方案或轻量高亮库，不为了一个代码块引入完整 IDE。

**默认页面骨架：**

```text
左侧：任务/会话列表与状态筛选
中间：任务目标、进度事件、公开工具活动和消息
右侧：文件、Diff、预览、产物与审批
底部抽屉：可展开日志，默认只显示摘要和错误定位
```

**Refero 自动匹配方向：** 搜索 `developer tools command center dark precise`，优先选择高对比、状态明确、边框层级清楚的 Style。具体视觉值来自最高分 Style；Refero 不可用时使用第 13.6.7 节 P7 的固定值。代码和日志使用等宽字体，说明文字使用无衬线字体。

**必须实现：** 任务持久化、重新连接、取消、重试、超时、日志分级、Diff、预览、权限与审批、外部影响摘要、失败恢复、成功产物、并发任务辨识、危险操作二次确认。

**不得使用：**

- 将模型私有思维链当作运行日志；
- 任务失败后只显示“Something went wrong”；
- 自动提交、发布、删除或部署却没有清楚的影响范围与确认；
- 为了“开发者感”把所有文字都设为等宽字体或降低可读性。

### 14.11 P8：消费者移动优先轻工具 Agent

**适用：** 单次改写、识别、规划、生活助手、轻量生成和非专业用户使用的小工具。

**默认代码方案：** shadcn/ui 基础组件 + 项目自行实现的单任务页面；只在品牌场景确实需要时，从 React Bits、Motion Primitives 或 Magic UI 选择 1—2 个轻量效果。不要套完整后台模板。

**默认页面骨架：**

```text
顶部：产品身份与少量必要入口
首屏：一句价值说明 + 唯一主输入 + 唯一主操作
结果区：可编辑结果、复制/保存/分享和再次生成
次级区：最近记录或示例，默认不抢占首屏
移动端：单列、底部主操作、44px 以上触控区域
```

**Refero 自动匹配方向：** 搜索 `consumer utility mobile friendly minimal`，并自动追加具体生活场景关键词。优先选择单任务突出、触控友好、卡片数量少的 Style。具体视觉值来自最高分 Style；Refero 不可用时使用第 13.6.7 节 P8 的固定值。

**必须实现：** 无登录试用或清楚登录时机、输入示例、实时校验、处理中状态、结果编辑、复制成功反馈、失败恢复、历史为空、移动键盘与安全区、额度或付费提示。

**不得使用：**

- 让用户先填写复杂配置才能看到价值；
- 首屏出现多个同等级 CTA；
- 使用大量玻璃拟态、发光和漂浮卡片掩盖简单任务；
- 为一个单功能 MVP 引入多租户 SaaS 模板。

### 14.12 附加方案：官网、SaaS 外壳和混合产品

**官网或发布页：**

- 主方案：[Launch UI](https://github.com/launch-ui/launch-ui)，用于 Hero、特性、案例、定价和 CTA；
- 备选：[Page UI](https://github.com/PageAI-Pro/page-ui)，用于 React / Next.js / Tailwind 营销区块；
- Magic UI、React Bits、MotionSites 只用于少量品牌动效；
- 官网可以更有表现力，登录后的高频工作区必须回到对应 P1—P8 方案；两者共用品牌色、字体和 Logo，不共用同等动效强度。

**SaaS 外壳：**

只有 PRD 明确需要团队、角色、订阅、账单、组织切换或完整设置中心时，才引入 SaaS Boilerplate 或仪表盘模板。否则只实现登录、个人设置和当前 MVP 必需页面，不为“未来可能需要”提前移植复杂外壳。

**混合产品：**

```text
主方案决定导航、页面结构、信息密度和 Token
次模块只占一个面板、抽屉或独立页面
共用同一套基础组件、图标、颜色语义和 Agent 状态
不得把两个模板各自的导航、主题、依赖和状态系统同时保留
```

示例：视频 Agent 同时支持对话时，采用 P4 创作工作区，把对话作为右侧可收起面板；不要以 Chat SDK 为整站骨架，再把视频编辑器塞进一条消息。

### 14.15 AI 的一次性执行卡

收到新 PRD、无设计稿项目或已有粗糙 MVP 时，直接执行：

```text
1. 运行现有项目；新项目则先建立可运行骨架。
2. 提取视觉 DNA，判断用户、领域、最终产物与主工作区。
3. 从 P1—P8 自动选择一个主方案；需要时选择一个次模块。
4. 按第 13.6 节搜索并评分 Refero Styles，自动选定一个具体 Style。
5. 读取其 DESIGN.md、Tailwind、CSS Variables 和 Design Tokens，转换为项目 Semantic Token。
6. 打开其他候选代码仓库，核验 LICENSE、版本、维护、安全和依赖。
7. 生成项目 DESIGN.md，写入方案编号、Refero URL、评分、页面骨架、Token 和复用边界。
8. 真实修改基础组件、Agent 状态和代表页面，清除外部品牌与硬编码样式。
9. 保持真实业务闭环可用，再将同一设计系统扩展到其余页面和状态。
10. 在 390px 与 1440px 真实浏览器截图检查并至少自动修正一轮。
11. 执行类型、Lint、测试和生产构建；记录许可证与第三方资产。
12. 用产品语言汇报已完成内容、选用的设计规范、未联调部分和真实风险。
```

完成这 12 步后才算“完成视觉选型和落地”。只给产品经理返回几个网址、几张截图、配色建议或三套方案让其选择，不算完成；只生成 `DESIGN.md` 而没有修改真实代码，也不算完成。

## 15. 响应式布局

如 PRD 未指定，至少检查以下宽度：

- 390px；
- 768px；
- 1280px；
- 1440px。

必须遵守：

- 桌面侧栏在手机上变为抽屉或适合移动端的导航；
- 抽屉关闭后不能留下遮挡层；
- CSS 可见性与 React 开关状态一致；
- 弹窗在小屏可滚动，主要按钮始终可达；
- 表格在小屏改成卡片、分组或受控横向滚动；
- 媒体和固定宽度元素不能撑破屏幕；
- 触控目标建议不小于 44×44px；
- 软键盘弹出后仍能看到当前输入和提交入口；
- 不出现意外横向滚动；
- 核心流程的所有页面和弹窗都要检查，不只检查首页。

## 16. 无障碍最低标准

- 使用语义化 HTML；
- 表单项关联 Label；
- 核心操作支持键盘；
- 焦点状态清晰；
- Dialog 管理焦点并在关闭后正确返回；
- 状态不只依靠颜色；
- 图片具有合适的替代文本；
- 装饰图标不重复朗读；
- 文字具有足够对比度；
- 动画尊重“减少动态效果”；
- 错误可被辅助技术识别并定位；
- Agent 进度可以适度播报，但不能逐 Token 打扰用户。

使用成熟组件只能降低风险，不能代替实际键盘和焦点检查。

## 17. 前端安全与隐私

### 16.1 禁止进入浏览器的内容

- 模型 API Key；
- 数据库凭证；
- 第三方私钥；
- 私密系统提示词；
- 管理员凭证；
- 仅应由服务端执行的权限规则。

### 16.2 环境变量

- `NEXT_PUBLIC_` 只放公开配置；
- 所有密钥留在服务端；
- 开发、测试、生产地址集中配置；
- 不把 `.env` 和真实凭证提交到版本库。

### 16.3 鉴权

- Web 默认优先安全的 HttpOnly Cookie；
- 不将长期令牌保存在 Local Storage；
- 同时处理 XSS、CSRF、会话过期和退出；
- 后端执行最终权限判断；
- 前端隐藏按钮不等于权限控制。

### 16.4 不可信内容

- 模型输出和用户输入默认不可信；
- Markdown/HTML 安全过滤；
- 不把未经处理的内容直接注入 DOM；
- 外部链接使用安全属性；
- 文件名和 URL 做安全处理；
- 日志和埋点不记录完整私密提示词、密钥和文件内容。

### 16.5 高影响操作

扣费、发布、群发、覆盖、删除和外部系统写入必须：

- 清楚展示影响；
- 用户进行最终确认；
- 前后端共同防重复；
- 后端重新校验权限；
- 保留结果或审计入口。

## 18. 性能默认规则

- 先测量再优化；
- 首屏不加载无关大型库；
- 编辑器、图表和媒体工具按需加载；
- 图片使用合适尺寸、格式和懒加载；
- 媒体预留尺寸以减少布局跳动；
- 大列表分页或虚拟化；
- 流式内容节流或批量更新；
- 避免相同接口重复请求；
- 大型二进制数据不长期放在 React State；
- 清理事件监听器、定时器、流式连接和 Object URL；
- 普通办公电脑和常见手机上核心流程不能明显卡死。

MVP 不要求为了性能提前复杂化，但不接受明显页面冻结和内存泄漏。

## 19. 日志、错误监控与产品分析

### 18.1 前端错误至少保留

- 时间；
- 页面和功能；
- 错误码；
- 请求 ID 或任务 ID；
- 应用版本；
- 是否可恢复。

错误信息不得包含访问凭证、完整隐私输入和私密生成内容。

### 18.2 产品行为事件

只有 PRD 已定义业务指标时才增加埋点。事件使用业务名称，例如：

- `generation_submitted`；
- `task_confirmation_completed`；
- `artifact_downloaded`；
- `generation_failed`。

埋点失败不能阻塞产品主流程。

## 20. 测试和代码质量

### 19.1 必须具备的脚本

新项目至少提供：

```json
{
  "scripts": {
    "dev": "next dev",
    "lint": "eslint .",
    "typecheck": "tsc --noEmit",
    "test": "vitest run",
    "test:e2e": "playwright test",
    "build": "next build",
    "start": "next start"
  }
}
```

具体命令可按实际框架调整，但能力不能缺失。

### 19.2 测试分层

| 层级 | 必测内容 |
|---|---|
| 单元测试 | 状态映射、数据转换、表单校验、错误归一化 |
| 组件测试 | 加载、空、失败、禁用、确认和提交交互 |
| 集成测试 | 页面通过适配层完成业务操作 |
| E2E | 至少一条核心用户闭环 |
| 人工浏览器检查 | 视觉、媒体、响应式、Console、Network 和恢复 |

不要追求无意义的覆盖率数字。优先测试昂贵操作、复杂状态和真实核心流程。

### 19.3 每阶段必须运行

```bash
npm run lint
npm run typecheck
npm run test
npm run build
```

核心闭环就绪后再运行 E2E。

新项目必须全部通过。已有项目如果存在与当前任务无关的历史问题，应区分：

- 本次新增问题：必须修复；
- 本次修改范围内的问题：必须修复；
- 既有问题：准确记录，不得冒充全部通过，也不得擅自扩大范围破坏其他功能。

## 21. 真实浏览器检查

编码后必须真正启动应用并检查，不得只阅读源代码或只执行 Build。

### 20.1 页面检查

- 所有目标路由可访问；
- 页面没有白屏；
- Console 无新增错误；
- Network 无意外失败和重复请求；
- 导航、弹窗、菜单、侧栏和滚动正常；
- 桌面端和移动端布局正常；
- 图片、视频、音频和下载真实可用。

### 20.2 状态检查

至少验证：

- 初始；
- 加载；
- 空；
- 提交；
- 排队或运行；
- 等待用户；
- 成功；
- 失败；
- 断线；
- 刷新恢复。

后端暂时无法制造的状态可以通过与真实类型一致的 Fixture 检查 UI，但最终核心成功路径必须真实联调。

### 20.3 核心业务闭环

```text
用户进入核心页面
→ 提供输入
→ 成功创建真实任务
→ 看见任务状态变化
→ 完成用户确认（如有）
→ 看见真实产物
→ 刷新后仍能恢复任务和产物
```

只展示 Fixture 不算完成真实闭环。

## 22. AI 自动分阶段开发方式

AI 根据项目大小调整阶段，但必须按“可运行的纵向业务闭环”拆分，不能先写完所有静态页面再统一接接口。

### 阶段 0：理解和落地决策

自动完成：

- 阅读需求和代码；
- 识别核心业务闭环；
- 提取视觉 DNA，从第 14 节选择一个主方案包；
- 按第 13.6 节自动搜索、评分并选定具体 Refero Style；
- 检查可复用模板、组件和动效的许可证与兼容性；
- 新项目生成 `DESIGN.md`，已有项目校验并补齐设计规则；
- 确定页面、路由、组件和接口边界；
- 建立任务状态映射；
- 确定本阶段验收方式。

这一步是 AI 的内部技术工作。没有关键业务冲突时，不等待产品经理确认技术选型，直接继续。

### 阶段 1：工程骨架和代表页面

- 工程、布局和导航；
- 设计变量和基础组件；
- 将选定 Refero Style 转换为项目 Semantic Token 并真实写入代码；
- 将复用资源统一适配为项目 Token 和组件规则；
- 环境配置和 API 客户端；
- 一个代表性的核心页面；
- 基础响应式；
- Lint、类型、测试和构建配置。

### 阶段 2：第一条真实业务闭环

- 核心输入流程；
- 创建任务接口；
- 运行、成功和失败状态；
- 至少一种真实产物；
- 可重复的核心流程测试。

### 阶段 3：Agent 完整交互

- 流式输出或轮询；
- 等待用户确认；
- 取消和重试；
- 断线和刷新恢复；
- 多任务、历史或任务中心（PRD 需要时）；
- 部分成功和未知状态。

### 阶段 4：质量和发布准备

- 完整响应式；
- 无障碍；
- 多媒体异常；
- 性能和资源清理；
- 安全和隐私；
- 真实后端联调；
- 自动检查和浏览器检查；
- 已知问题清单。

小型 MVP 可以合并阶段，但不得跳过状态、联调和检查。

## 24. 完成标准 Definition of Done

只有同时满足以下条件，才能把一个前端阶段标记为完成：

### 功能

- PRD 本阶段功能已经实现；
- 至少一条核心流程可真实操作；
- 接口、任务和产物没有使用静态假结果冒充；
- 高影响操作有确认和防重复。

### Agent 状态

- 加载、空、运行、等待、成功和失败有明确界面；
- 断线和刷新不会轻易丢失后端任务；
- 未知后端状态有安全兜底；
- 用户能理解当前状态和下一步。

### 界面

- 已生成或更新项目 `DESIGN.md`；
- 没有正式品牌规范时，已经自动选定并记录一个具体 Refero Style，或明确记录使用第 13.6.7 节的兜底 Token；
- AI 没有要求产品经理决定主色、字体、圆角、阴影、深浅主题或设计规范；
- 页面符合已确定的视觉 DNA，而不是通用 AI 默认样式；
- 复用的模板和组件已经去除原品牌内容并统一到项目 Token；
- `DESIGN.md` 中的 Token 已经真实应用到基础组件、核心页面和 Agent 关键状态，不是只停留在文档中；
- 已有 MVP 的路由、接口、权限、表单和真实业务闭环在视觉改造后仍可用；
- 所有代码和素材来源均有明确使用许可；
- 桌面和移动目标宽度可用；
- 无意横向滚动和遮挡；
- 基础键盘操作与焦点正常；
- 媒体加载和失败有处理；
- 文案使用产品语言。

### 工程

- 无本次新增 Lint 错误；
- 无本次新增类型错误；
- 测试通过；
- 生产构建通过；
- Console 无新增错误；
- 没有在前端暴露密钥；
- 没有遗留无说明的临时 Mock、TODO 和调试代码。

### 交付

- 汇报真实完成内容；
- 汇报执行过的检查及结果；
- 明确尚未真实联调的部分；
- 明确剩余问题和影响；
- 不因“页面能打开”或“构建成功”夸大完成程度。

## 25. 禁止的实现方式

AI 不得采用以下做法：

1. 把技术选型重新交给不懂开发的产品经理；
2. 输出多套技术方案后停止，不进入开发；
3. 只实现正常成功页面；
4. 加载尚未完成时显示空数据；
5. 用前端动画、计时器或连接状态推断后端任务已经成功；
6. 把真实任务状态只存在 Local Storage；
7. 在页面组件中到处散落接口请求；
8. 用 CSS 隐藏代替后端权限控制；
9. 把密钥写入 `NEXT_PUBLIC_`；
10. 默认模型不在选项中时静默选择第一项；
11. 桌面侧栏直接缩小后当作移动端；
12. 使用 Fixture 或 Mock 后宣称真实联调完成；
13. 构建成功后不做浏览器检查；
14. 为了符合目录模板而重写稳定的已有项目；
15. 用大量 `any`、禁用规则或忽略错误制造“检查通过”；
16. 未经用户要求修改当前任务之外的大量代码；
17. 将内部推理、私密提示词或供应商日志直接显示给用户；
18. 不分析产品场景，给所有 Agent 产品套同一套中性 SaaS 风格；
19. 把 Refero、CollectUI 等视觉参考站误认为开源代码仓库；
20. 未检查许可证就复制模板、组件、图片、字体和视频；
21. 同时拼接多套模板、组件库和动效库，造成视觉与工程不一致；
22. 从外部模板复制代码后保留原品牌、硬编码颜色和无用依赖；
23. 要求产品经理浏览大量设计网站并自行决定视觉方案；
24. 只写“高级、简洁、科技感”，却不生成可执行的 `DESIGN.md`；
25. 询问产品经理主色、辅助色、字体、字号、圆角、阴影、间距或深浅主题；
26. 给产品经理提供多套 Refero Style、配色方案或风格截图，要求其选择后再开发；
27. 已经选定设计规范，却只输出建议、Prompt 或 `DESIGN.md`，不修改真实前端代码；
28. 为套用外部风格而破坏已有 MVP 的路由、接口、权限、状态或核心业务闭环；
29. 将 Refero 的品牌名称、Logo、截图、商业字体和文案原样带入当前产品。

## 26. AI 最终汇报格式

完成一个阶段后，使用简短、非技术化的格式汇报：

```markdown
## 已完成
- 用户现在可以完成什么。

## 已检查
- 电脑端：通过 / 存在问题
- 移动端：通过 / 存在问题
- DESIGN.md：已生成或更新 / 不适用
- 自动视觉规范：Refero Style 名称与 URL / 使用确定性兜底 Token / 沿用正式品牌规范
- 开源代码与素材许可：已检查 / 未使用外部资源 / 存在问题
- 真实接口：通过 / 尚待后端
- Lint：通过 / 具体问题
- 类型检查：通过 / 具体问题
- 测试：通过 / 具体问题
- 构建：通过 / 具体问题

## 还没有完成
- 尚未完成内容及原因。

## 需要产品决定
- 只列真正的业务选择；没有则写“无”。
```

不要把大量文件名、库名和实现细节放在汇报最前面。先说明产品结果，再补充必要技术信息。

## 27. 本手册的最终执行原则

1. 产品经理提供需求，AI 负责前端技术实现；
2. 新 Web 项目直接使用统一默认栈；
3. 已有项目优先兼容，不做无理由重写；
4. 缺少设计稿时，根据产品视觉 DNA 和最终产物，从第 14 节自动选择方案包，并按第 13.6 节自动匹配具体 Refero Style；
5. 缺少后端时先建立可替换契约，不停止前端开发；
6. 技术问题由 AI 决定，产品问题才询问产品经理；
7. 按可运行的业务闭环分阶段开发；
8. Agent 的运行、等待、失败和恢复是核心功能；
9. 后端是任务状态和结果的最终事实来源；
10. 自动检查与真实浏览器检查缺一不可；
11. Fixture 可以帮助开发，但不能代替最终真实联调；
12. 最终汇报必须准确，不隐藏问题，不夸大完成度；
13. 优先复用许可明确、兼容且成熟的模板、组件与动效；
14. 视觉参考与开源代码严格区分；
15. 每个项目建立自己的 `DESIGN.md`，将外部参考转化为本项目规则；
16. 产品经理不负责前端审美选择，AI 负责自动匹配、实现和自检；
17. 视觉规范必须真实落到代码；只给建议、候选方案或设计文档不算完成；
18. 已有 MVP 的视觉上线改造必须保留并回归验证真实业务功能。

当本手册与具体项目技术细节不一致时，AI 应在不改变产品目标的前提下做出最小、稳妥的适配，并继续执行；只有真正的业务冲突才需要产品经理决定。
